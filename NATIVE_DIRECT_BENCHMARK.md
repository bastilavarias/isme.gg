# Native Direct benchmark

As of v0.2.0, the experimental transport is available in both debug and release builds. Native Direct now defaults on for unset preferences; existing choices are preserved. Settings > Experimental playback allows switching back to Legacy HTTP. The provider is private in both build variants. Diagnostic logs and the modal preview remain debug-only. The original benchmark below describes the experimental implementation; its algorithms and limits are unchanged.

## Implementation
Native Direct reuses the pinned Flutter video_player / Android Media3 integration via VideoPlayerController.contentUri. A non-exported ContentProvider exposes a read-only seekable Android StorageManager proxy descriptor. Requests are served by a bounded number of worker threads and the same TorrentEngine selected-file cache. Reads check generation, cancellation and verified piece availability before copying bytes. File length and EOF respect the selected video, including multi-file piece boundaries. The provider does not expose paths or grant permissions. Switching or leaving playback cancels active direct readers before disposing the decoder. Legacy HTTP remains unchanged.

This is an alternative native transport using Media3's existing content data source, not a bespoke Media3 DataSource or a rolling cache. The loopback HTTP control/catalog API remains. The same 7 GiB limit, storage guards, source selection, recovery budget, and 45-second initialization timeout remain. Direct reads have a 35-second bounded wait per callback, and may still fail if the media data is not available. FUSE support, seek performance, cancellation and kernel read behavior on specific Android devices must be validated. No guaranteed performance improvement. No transparent fallback within an experimental attempt: select Legacy HTTP manually to keep the comparison clear.

## Fast startup experiment

The Fast startup preference defaults on unless explicitly set; Settings > Experimental playback allows choosing it independently. It is ignored for HTTP. Disable it to compare with the original Native Direct transport. On metadata validation, the native scheduler assigns staggered deadlines to missing pieces covering up to the first 2 MiB of selected media (at most 8 pieces; actual verified pieces may extend beyond that byte window). As Media3 reads beyond this window, including noncontiguous container reads, the old deadlines are cleared and a new bounded window is scheduled. The readiness gate remains the first verified piece, so this does not intentionally increase initial buffering. When initialization finishes or the session is cancelled, deadlines are cleared; normal sequential behavior continues. A 110-second guard also clears them on subsequent reads. Native deadline errors disable the optimization rather than failing playback.

The deadline API is verified against libtorrent4j 2.1.0-39. This is a best-effort scheduling hint, not a guarantee of peer delivery or throughput. No new media sources, extra sessions, or changes to storage limits, cache cleanup, player timeouts or decoder configuration. Benchmark on authorized media. Logs include fastStartup=true/false, startup-window first/last/missing and startup-window-finished. Compare matched starts with the switch on and off, including failed attempts and seeking/continuous playback.

## Adaptive buffering experiment

Native Direct has a separate Adaptive buffering switch (default on unless explicitly set). For the previous Fast Startup baseline, switch Adaptive buffering off. For the original Native Direct baseline, turn both switches off. HTTP ignores the experiments.

After initialization and an optional initial resume seek, the app samples the native maximum completed read wait and initialization time. The startup guard targets 2.5 seconds of reported buffer for healthy starts, 6 seconds for delays of at least 3 seconds or resume, and 10 seconds for delays of at least 10 seconds. The additional hold is bounded to eight seconds (plus a native status sample capped at 600 ms). It does not require a full buffer if the cap expires. Unknown telemetry bypasses the hold unless the player reports buffering (then at most two seconds). The pinned Android plugin polls buffered position every second, including while paused. This is reported buffered duration, not verified contiguous media bytes or a first-frame measurement.

With both experiments enabled, the initial priority window remains active through the resume seek and until first observed playback advancement (or pause, cancellation, or the existing native startup time guard). While playing, a low reported buffer below 2.5 seconds or buffering state raises priority for upcoming reads; it clears at 6 seconds of buffer when no longer buffering. The native lease expires after 6.5 seconds without renewal, and clears on pause or cancellation. This uses the same bounded deadline window, not a second download/session. Media3 still owns decoding, ordinary rebuffering and load-control; no additional pause/play loop and no custom Media3 LoadControl. The original 35-second read deadline, storage checks and recovery budget remain. A shortage of available media data can still cause stalls, and resume buffer telemetry may lag a seek.

Logcat: start/result lines now include adaptiveBuffering=true/false. adaptive-startup reports targetMs, heldMs, aheadMs, readWaitMs and resuming. buffer-urgency=true/false and buffer-window identify runtime hints. rebuffer-start/end count sampled stalls (2-second watchdog sampling, so brief stalls may be missed and durations are approximate). Compare the same authorized media on the same physical device, at the same playback position, alternating the switch on/off for several cold starts. Include time to playback, stall count and time, seek/resume and cleanup. No guaranteed improvement; thresholds are experimental and may increase startup delay in exchange for stability.

## Benchmark
1. Use a debug build and identical authorized media on the same physical device. If possible use the exact same source and start position. Run modes sequentially, not simultaneously. Record 3–5 cold starts per mode.
2. Use the Settings selector to switch modes. Start a fresh playback each time. Capture IsmePlayback, IsmeDirect, IsmeTorrent, IsmeLocalServer and ExoPlayer logs separately.
3. The start line identifies transport, attempt and candidate index; initialization line reports selected file bytes, elapsed readiness and HTTP probe times (null for direct). The playing line reports initialization, play request and first observed forward position change. Timings are cumulative within each attempt, not true first rendered frame; firstAdvanceMs is sampled every two seconds. Use wall-clock timing to first visible frame and include failed attempts when comparing total startup.
4. Inspect direct read slow/failed logs with offset, bytes and waitMs. Test seek backward/forward, resume, subtitles/audio, repeated open/close, next episode and low storage. Verify cleanup and no stale session data. Repeat on ARM64 phone and real Android TV; emulator is functional coverage only.
5. Do not publish or make direct the default without passing runtime tests and reviewing measurements.
